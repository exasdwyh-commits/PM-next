## Muse Glimmer 本机真实部署（main @ ff5cec46）
- **模型身份确认**：文档只写 modelId=muse-glimmer。实为 Meta 30B dense Apache-2.0，
  HF `meta-models/Muse-Glimmer-30B-GGUF`，选 Q4_K_M（16GB，文件名含 "17GB" 实际 16G）。
- **硬件**：本机 Apple M5 Pro / 64GB 统一内存，30B Q4 完全够跑。
- **网络坑**：`huggingface.co` 在本机代理下 502/连接失败；`hf-mirror.com` **直连可用**。
  下载必须：`env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy HF_ENDPOINT=https://hf-mirror.com hf download ...`
- **运行时**：llama-cpp-python 0.3.35，`CMAKE_ARGS="-DGGML_METAL=on" pip install "llama-cpp-python[server]"`。
  Metal 确认方式：查 `libggml-metal.dylib` 里是否有 `_ggml_backend_metal_init` 符号（查 libggml-base 会误判为无）。
- **关键坑（Harmony 格式）**：Muse 是 Harmony reasoning 模型，输出形如
  `to=self<|message|>思考<|start|>assistant to=user<|message|>答案<|eot|>`。
  llama-cpp-python 自带 server **只渲染不解析** → 思维链混进 content。
  自写 `scripts/muse-openai-server.py` 做渲染+解析（reasoning_content / content 分离）。
  解析 bug：`to=\w+` 会把答案开头数字吃掉（"1+1=2"→"+1=2"），须限定已知 recipient。
  另有：`re.escape(MESSAGE)+">"` 多拼一个 `>` 导致匹配失败（MESSAGE 常量本身已含 `>`）。
- **接线**：.env 设 `MODEL_PROVIDER_MUSE_LOCAL_BASE_URL=http://127.0.0.1:8080/v1`、
  TIMEOUT 120000、MAX_TOKENS 4096（reasoning 模型 token/耗时都大）。
  Model Control 用 `SAVE_PROFILE` 启用（**必须带 displayName 等完整字段**，只传 key+enabled 会 422）。
- **端到端实证**：`ModelRun` = ASSISTANT_DIALOGUE → assistant-dialogue-resident →
  muse-glimmer-resident-slot，provider=muse-local，SUCCEEDED，67631ms，usage 492in/808out。
  模型明确回答"当前数据未覆盖"而不编造 → 人格硬约束在真实 30B 上生效。
- **坑**：改 .env 后 Next dev 热重载会报 `TypeError: a[d] is not a function`（chunk 错乱），重启 dev 即可。
- Laya 侧：三个 checkpoint 完整（804M/614M/804M），服务 :8000 常驻，/v1/systemone 正常。
