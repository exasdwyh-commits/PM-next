# Kern 成熟强化优先：施工路线 V2

日期：2026-10-15<br>
依据：本轮用户确认的推进原则，以及《Kern与Bops源码核对及改进方案-2026-10-15.md》。<br>
状态：第一批 A1 连接器安全强化已交付 PR #102，6/6 CI 通过，未合并／部署；正继续 A2 可靠性强化。下文保留完整路线，不能把单批交付视为整个阶段完成。上一轮源码指纹是评审快照，不视为施工时的最新状态。

## 一、总原则

**先把已有功能做稳、做完整、做成闭环；再让前端更好用，再吸收外部成熟能力；最后处理高成本、高耦合的难点。**

成熟强化不是停止提高能力。已有能力如果能更稳定地执行、减少人类返工、正确恢复并交付可信结果，就是实际能力提升。

Bops 是重要参照，不是要替换 Kern 的基座。学习不限于界面，也包括任务组织、工具选择、等待与恢复、咨询方式和低成本变化观察。吸收方式以独立设计实现为主，不复制受限核心代码与素材。

## 二、统一的“成熟”标准

每个功能都检查以下七项，而不是“有页面／有接口／单测绿”就算完成：

1. **入口明确**：用户从哪里发起，使用现有对话／页面，不另开重复入口。
2. **真实可执行**：输入、模型、执行器、权限、运行环境均可用；不可用给出真实原因。
3. **过程可信**：区分排队、运行、等待、失败、已结束和成功。
4. **受阻可恢复**：缺输入、需批准、断线、超时、重启都有明确后续，不无限空转。
5. **安全可控**：组织与会话隔离、动作授权、单次凭据、数据出站与高风险操作有边界。
6. **结果可交付**：回到原会话，有产物／证据／验证结论，不把模型生成当事实验证。
7. **可复验**：失败、重放、并发、取消和跨会话场景进入回归；在同一候选 head 上验收。

## 三、阶段 A：现有能力成熟强化——当前主线

### A0：先统一施工与验收基线

- 重新核对工作树、HEAD、未提交改动、已有分支成果及实际运行实例。
- 指定一个最终候选，不 reset、不覆盖他人 WIP、不把不相关改动打包混合。
- 建立功能台账：已实现／待集成／待验收／环境阻塞／确实缺失。
- 对 U01 连接器信任加固、批准卡成果优先核对复用，避免重复开发。

**验收门槛**：每项结论可追到实际文件、提交、测试与目标实例；本地 origin/main 不冒充远端实时状态。

### A1：安全与写操作闭环

- 交付并验证已有连接器信任策略修复，包括已保存工具快照的刷新与重新分类。
- 对 shell、Codex、文件覆盖／移动、AppleScript、剪贴板、外部发送分别列出风险矩阵。
- 复用现有 actionHash、ApprovalGrant 和 ToolBroker，不新增第二套批准引擎。
- 审核批准／拒绝／过期／参数变化／凭据重放／并发点击／撤权语义。
- 明确“全委托≠业务批准≠执行批准≠结果接受”。

**验收门槛**：未批准不执行受保护动作；旧凭据不允许执行变更后的动作；拒绝与失败不产生虚假成功回执。

### A2：任务执行与 Worker 恢复

- 按现有路径分别核对：聊天直派、Mission、产品研发、本机执行。
- 区分“角色存在”“可路由”“执行器 ready”“真正执行成功”。
- 核查任务领取、租约／心跳、超时、重试预算、取消与孤儿恢复，优先复用已有机制。
- 保证重复请求不重复创建任务，重复回调不重复发结果。
- 非关键失败、关键失败与 QA 未通过，不混成同一种完成状态。

**验收门槛**：任务不能静默丢失或永久假运行；重试不重复副作用；取消后不能悄悄继续执行新动作。

### A3：输入→证据→QA→报告→业务采纳

- 复查建品提议、批准回执、证据归档及报告生成链。
- 不把报告“已生成”当作“可交付”，不把 QA 完成当作业务 Gate 已批准。
- 页面、会话卡片、下载产物的质量状态一致。
- 有缺项保留 UNKNOWN 并给出下一步；不要用润色掩盖证据不足。
- 区分历史验收报告与本轮亲自复跑结果。

**验收门槛**：最终交付能说明做了什么、依据是什么、哪些未证实、用户还需决定什么。

### A4：已有定时能力可靠性

- 复用现有 DAILY_BRIEF／REMINDER／MISSION 与 Worker schedule hook。
- 检查认领 slot 后、实际执行前崩溃的恢复语义；必要时补持久化运行记录／Outbox。
- 验证同 slot 幂等、错过时间、时区／夏令时、暂停恢复、失败退避与停用提示。
- 本项是已有功能强化，不重新开发另一套 Routine。

**验收门槛**：后台任务可持续推进；执行失败可见；重启不静默丢工作，重放不重复发送或启动。

### 阶段 A 放行条件

选择一个固定最终候选，至少跑通：

1. 聊天专家任务：真实 readiness→执行→回原会话。
2. Mission 研究：专家执行→证据→独立 QA→报告→待业务批准。
3. 本机任务：确认→领取→执行→验证→回执，含拒绝与过期。
4. 定时任务：触发→恢复／去重→结果或可见失败。

高风险写操作先用受控测试夹具验证，不为验收而真实付款、发布或删除用户数据。

## 四、阶段 B：前端成熟化与执行体验吸收

这是既有业务能力的前端整合，不先做一轮脱离状态语义的纯换皮。

### B1：一个目标，一张任务卡

- 复用 Mission／AgentTask／AgentRun，建立统一聚合读模型，不新增平行状态机。
- 默认只展示目标、真实进展、阻碍、下一步、产物和需要用户处理的事项。
- 员工、节点、工具调用与尝试次数默认折叠，保留专业下钻。
- 排队与运行分开；成功、失败、跳过与已结束分开。

### B2：统一“需要你”

- 优先整合现有提议、执行批准、Mission 问答等入口。
- 卡片说清楚：为什么停、用户做什么、处理后恢复哪里。
- 刷新／切会话不丢失、不串卡；过期或旧 revision 的卡不能恢复新任务。
- 介入事项独立查询与分页，避免仅查最近任务导致长期待办不可见。
- 登录／2FA／CAPTCHA 卡只有在后端识别与恢复链路可用时才宣传支持。

### B3：结果和可访问性

- 会话结论、报告页面、下载使用一致的产物与质量状态。
- 复用设计令牌，检查亮暗主题、对比度、移动端、键盘与屏幕阅读器操作。
- 借鉴 Bops 的清晰交接与简洁反馈，但保留 Kern 的专业证据与审计入口。

**阶段 B 验收**：用户不必先学 Agent／DAG／Runtime 就能完成任务；前端不夸大后台能力；正常、等待、失败、恢复、取消均有真实界面验收。

## 五、阶段 C：低风险、高复用的能力吸收

按增量、可独立回滚的方式做，不一口气扩大自动化范围。

1. **工具选择优化**：已授权 API／连接器→搜索与文本→受控文件／命令→DOM→视觉；不是所有任务都需要操作电脑。
2. **统一能力目录**：先统一聊天、Mission、研发流程的 readiness 与可执行范围，再开放一个最有价值的新专家入口。
3. **轻量专家咨询**：一层、只读、上下文显式授权、预算与超时；不转移任务所有权，不绕过独立 QA。
4. **一个结构化 Watch**：先检测变化，变化才调用模型，去重后再通知；复用 Worker、证据与注意力机制。

**阶段 C 验收**：每新增一项，都有真实受益场景、权限边界、成本记录、失败回退与独立回归。没有这些条件则保持未启用，而不是为了功能表好看而开放。

## 六、阶段 D：最后攻克困难能力

前述阶段稳定后再选，不默认全部立项：

- 完整视觉 Computer Use 与安全的人工接管／交还。
- 多执行主机及任务迁移、跨机器租约和结果交接。
- Orgo 或其他云电脑供应商适配。
- 多专家复杂自动协作与长期自主任务。
- 动态创建角色与更广泛的邮件／电话／渠道执行。

每项先做最小技术验证，再决定产品投入。新主机、新权限、新供应商成本不能借“前端学习”顺带引入。

## 七、排期和工作方式

- 当前实施优先级：**A0 → A1 → A2／A3 → A4 → B → C → D**。
- 阶段 A 内，独立检查可并行；同一执行链的状态、权限和界面改动要按依赖串行。
- 阶段 B 的交互草图可提前准备，但不同时重构尚未稳定的后台状态与界面。
- 阶段完成以验收证据为准，不以时间到期为准。
- 新发现只进入分级台账，除安全与关键阻断外，不随意打断当前闭环扩 scope。
- 不删除现有专业后台，不削弱 Evidence／QA／Governance，不复制 Bops 核心代码。
