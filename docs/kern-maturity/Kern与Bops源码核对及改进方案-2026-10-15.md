# Kern × Bops：源码核对及分阶段改进方案

日期：2026-10-15<br>
性质：只读架构／产品评审；未修改 MCP 主机上的项目源码，未提交、合并或部署。<br>
参考输入：用户附件《未命名 4.md》、Bops 仓库源码、MCP 主机当前 Kern 源码及抽样验收工作树。

## 一、结论先行

**参考文档的方向基本正确，但不能直接作为施工清单。Kern 已经实现了其中不少基础能力，当前最需要的是“交付基线收敛＋执行体验整合”，而不是再造一套 Agent、Session 或 Approval。**

建议顺序：

1. **P0：先核对并交付已经写好的安全修复与批准卡成果，明确唯一验收版本。**
2. **P1：在既有 Mission / AgentTask / AgentRun 之上建立统一的用户任务视图。**
3. **P1：统一“需要你”卡片及恢复流程，补齐动作风险分类。**
4. **P1：用统一能力目录连接聊天路由与真实执行器，再逐步开放专家执行。**
5. **P2：补轻量专家咨询，强化现有定时任务可靠性，再实现变化观察 Watch。**
6. **P3：真实需求出现后再扩 Execution Host；暂不接入 Orgo 云电脑。**

Bops 最值得借鉴的是“用户看到一件事持续推进”的执行交互，以及直接能力优先、受阻才找人的组织方式。Kern 应继续保留自己的证据、独立 QA 和治理边界。

## 四、已经具备的能力与真正缺口

### 4.1 任务：不是缺 Mission，而是缺跨路径的一致用户对象

**已实现证据**（路径相对 PM-next）：

- `src/modules/supervisor/service.ts:39–55,103–207`：Mission snapshot、根任务、conversationId、sourceRunId、幂等 launch 与事件写入。
- `src/modules/supervisor/plan.ts:7–15,43–76`：可执行 DAG、节点状态、QA、Mission outcome。
- `prisma/schema.prisma:2105–2149`：AgentTask 父子关系与上下文。
- `prisma/schema.prisma:2911–2924`：KernMissionEvent 的递增 seq 和唯一约束。
- `src/modules/workforce/conversation-return.ts:19–40,54–83`：组织／创建人／会话归属核验，行锁与回执幂等。

**缺口判断**：Mission、聊天专家直派、本机任务都有执行机制，但用户层容易看到不同卡片、不同状态和不同回执。优先统一读取与展示，而非迁移掉这些已运行的路径。

**推荐设计：`TaskThreadView`（建议名，不是已实现对象）**

```text
TaskThreadView
  id / title / conversationId
  source: mission | specialist | desktop
  rootTaskId / relatedRunIds
  phase / latestActivity / updatedAt
  progress: succeeded / failed / blocked / skipped / pending
  blockers[] / requiredActions[]
  deliverables[] / evidenceSummary
  executionHost / canPause / canResume / canCancel
```

- Mission 优先沿用根任务 ID；独立任务使用稳定的带类型引用。没有跨任务生命周期需求前，不急于新增 ExecutionSession 表。
- 前端名称可以叫“任务”“这件事”，无需给用户暴露 Thread／Run。
- 写入仍走原服务；统一视图不可直接改任务状态。
- 统一事件外观时复用已有 Mission 事件；非 Mission 路径通过适配器映射，必要的持久化与去重另行设计，不能伪造已有事件。
- 展开后才显示角色、尝试次数、执行位置与审计。

**状态语义**：`RUNNING` 必须来自真实执行；等待队列、待输入、环境离线、失败不能混成“正在处理”。业务已生成报告、QA 通过、用户接受、业务 Gate 批准也不能合成一个“完成”。

**额外改进**：当前部分进度计算把 BLOCKED／FAILED／SKIPPED 算作“结束”；保留这种调度含义，但 UI 应区分“已结束节点”和“成功节点”，不显示误导性的“全部完成”。参见 `supervisor/plan.ts:78–103`、`muse/read-model.ts:195–215`。

### 4.2 人工介入：已有入口，缺统一契约

已存在：

- `src/modules/supervisor/attention.ts:14–66`：AUTO_HANDLE／WATCH／SURFACE／INTERRUPT，以及 Mission、Proposal、本机确认等信号。
- `src/modules/muse/read-model.ts:160–244`：聚合未回答问题、提议、本机待确认任务。
- `src/modules/muse/attention-feed.ts:32–61`：稳定通知 key、完成通知和定时失败通知。
- `src/app/muse/components/desktop-confirm-card.tsx`：本机确认卡。

**建议不是再做一个“需要你”页面，而是统一 `RequiredAction` 契约**：

```text
id / taskRef / conversationId
kind: MISSING_INPUT | DECISION | EXECUTION_APPROVAL | GOVERNANCE_APPROVAL
      | LOGIN | TWO_FACTOR | CAPTCHA | PAYMENT
summary / requestedBy / createdAt / expiresAt
allowedActions / resumeToken / revision
resolvedAt / resolvedBy / resolution
```

其中 LOGIN／2FA／CAPTCHA／PAYMENT 在当前 Kern 本轮检查范围内未见完整的桌面识别与接管链路，应列为能力新增，而不是仅加枚举就宣告实现。

要求：

1. 显示“卡住在哪、需要你做什么、完成后怎么继续”。
2. 点击响应只能恢复对应任务／节点／当前 revision；过期卡不得恢复旧运行。
3. 批准、拒绝、稍后、失败重试、并发处理、刷新恢复都有明确语义。
4. 普通 Blocker 不自动等于人类中断；能自动重试的故障应按预算退避。
5. 登录／验证码交给安全的人工或凭据注入通道；不写入模型上下文、日志与报告。
6. 持续观察的“WATCH 注意力级别”与“Watch 监控功能”要分清，不能用同名常量当成功能证据。

**规模风险**：当前注意力读取只取最近 12 个 Mission，问答事件最多 1000 条，本机概览 limit=20（`muse/read-model.ts:169–186,234`）。这不一定立刻造成故障，但长期待办量增加时可能漏掉旧阻塞项。应优先查“未解决介入项”，再独立分页最近任务；加入超过这些上限的回归用例。

### 4.3 审批：应补覆盖，不应再造引擎

**已实现**：

- `desktop-runtime/confirmation.ts:49–73`：shell 三档分类；agent.delegate 必须确认。
- `desktop-runtime/confirmation.ts:76–95`：actionHash、scope、1 小时 TTL。
- `desktop-runtime/service.ts:201–298,347–435`：确认、签发 grant、claim 时核验与消耗。
- `connectors/runtime.ts:110–125`：连接器调用携带 actionHash／grant，经 ToolBroker 执行，用后失效。
- `tests/desktop-confirm.test.ts:21–64`、`tests/kern-connectors.test.ts`：已存在相关测试。

**真实覆盖边界**：本机分类器目前专门处理 shell.run 和 agent.delegate；其他动作走 default AUTO。现有测试明确断言 `fs.write_text` 为 AUTO（`desktop-confirm.test.ts:37–40`）。这不等于整个系统没有其他保护，也不能称所有写操作都受同一种逐次审批约束。

**建议**：制作统一动作策略矩阵，而不是口头规定“读可执行，写必审批”。

| 动作类别 | 默认策略建议 | 补充约束 |
|---|---|---|
| 受信源、允许范围内读取 | 可自动 | 仍受数据访问授权、隐私及出站限制 |
| scratch 中可逆写入 | 可按任务授权自动 | 路径白名单、变更回执，不覆盖用户原件 |
| 覆盖／移动用户原文件 | 确认或明确窄授权 | 目标路径、冲突策略、备份／撤销 |
| 任意 shell／Codex 开放式委派 | 延续现有确认 | 完整命令／cwd／能力范围；必要时 sandbox |
| AppleScript／剪贴板／权限更改 | 单列风险 | 不从“不是 shell”推断为低风险 |
| 外部发送／发布 | 默认确认 | 收件方、正文摘要、组织与任务绑定 |
| 付款／采购 | 强制确认 | 收款方、金额、币种、上限、幂等与真实支付回执 |
| 业务事实采纳／Gate | 保留治理批准 | 全委托、任务接受或执行批准不能代替 |

**执行批准、业务治理、结果接受应是不同语义，底层可以共享既有安全凭据。**

### 4.4 专家组织：区分“会路由”与“能执行”

`assistant-runtime/dispatch-readiness.ts:28–33` 的聊天直派映射目前只有：

```text
tech_architect_agent → CODING → WORKER
```

`specialist-dispatch.ts:20–46` 又限定单一、低风险、readiness 已通过的专家。`collaboration-planner.ts:14–35` 和 `goal-plan.ts:27–39` 明确保留 Shadow／ADVISORY_ONLY 语义。

**这不表示其他专家完全不能执行**：它们还可以从 Mission 节点、产品研发流程等路径执行。问题是同一角色在不同入口的可执行条件不一致，不能拿 Mission 路径覆盖来证明任意聊天可自动派发。

建议把散落的角色、工具、模型和执行器元数据收敛为一个目录（建议 `AgentCapabilityRegistry`）：

- roleCode／taskClass／inputContract／outputContract；
- enabled entrypoints：chat／mission／product_rnd／consult；
- executorType、requiredCapabilities、模型策略、工具预算；
- 权限／风险／组织安装状态；
- health、最近真实成功时间、不可执行原因。

保留 Worker 处理器注册表的现有分层，不把领域逻辑塞回 Worker。参见 `worker/registry.ts:5–14,35–45`。

开放顺序：先技术架构直派稳定，再挑选输入输出最明确的只读市场／科学证据咨询小场景，逐个验证；不要一次把 13 个角色全部放开。

### 4.5 `consult_specialist`：新能力，但必须有硬边界

Bops 的 `askTeammate` 确实是一层调用，生成请求没有提供继续委派的工具；保留咨询轨迹并回到主对话。它还会拼入对方最近聊天、机器摘要与记忆，隐私限制有部分依赖提示词和自然语言匹配。Kern 可以吸收“一问一答”，但不照搬这种宽上下文共享。

建议最小契约：

```text
ConsultRequest: taskRef, question, expertCode, scopedContextRefs,
                deadline, tokenBudget, idempotencyKey
ConsultResult: answer, evidenceRefs, uncertainty, assumptions,
               conflicts, suggestedNextStep, receipt
```

- depth=1，在服务端执行；被咨询方不获得咨询／派发／写工具。
- 咨询不转移主任务所有权，不凭空创建完整工作流。
- 上下文必须显式 allowlist；跨产品、跨会话、跨组织的内容不能自动共享。
- 工具最小化；事实不够返回 UNKNOWN，专业意见不能直接升格为已验证事实。
- 超时、限额、并发、缓存键、权限与审计都纳入测试。
- QA 不能通过咨询“口头同意”替代独立验证。

### 4.6 Routine 已有，Watch 才是新增主线

现有 `schedule/service.ts` 已有：

- DAILY_BRIEF／REMINDER／MISSION；
- cron、timezone、启停、修改、删除；
- 原子抢占到期 slot，Mission 用 `schedule:<id>:<slot>` 再做 launch 幂等；
- 连续失败五次停用。

证据：`schedule/service.ts:16–23,93–160,234–306`；Worker schedules hook 在 `worker/registry.ts:69–74`。

**应先补的可靠性点**：`schedule/service.ts:276–287` 先推进 nextRunAt，再执行实际动作。如果进程在两者之间崩溃，本轮 slot 有丢失风险；本次未做 kill／重启实验，因此这是源码推导风险，不是已复现生产事故。

建议新增持久化 ScheduleRun／Outbox，唯一键 `(scheduleId, slot)`，状态包括 claimed／running／succeeded／failed，带 lease、重试和结果引用。提醒消息等非 Mission 副作用也必须幂等。补时区、夏令时、错过 slot、重启、重复 Worker 与人工暂停测试。

**Watch 第一版建议从结构化来源开始**：供应商报价接口／产品列表／指定研究检索／PR、CI 状态，而不是先做全屏视觉监视。

```text
观察源 → 获取快照／版本 → 与基线比较 → 规则过滤 → 必要时模型判读
      → SourceCapture／证据 → 去重事件 → 安静汇总或“需要你”
```

建议实体：WatchDefinition、WatchCheckpoint、WatchObservation；包含范围、频率、baseline hash／cursor、最近成功抓取、已通知指纹、cooldown、预算和失败退避。

Bops 值得借的关键是“先检测变化，发生变化才付出模型成本”。Kern 不宜直接移植其进程内定时器；长期任务继续用现有独立 Worker 与持久化状态。

### 4.7 Execution Host：先诚实展示现有能力

当前本机 runtime 有文件、shell、Git、打开浏览器、App、剪贴板、AppleScript、Codex 等能力。`desktop-runtime/extended-actions.ts:1–6` 明确写着 Computer Use 扩展仅为骨架，不能称为已完成的视觉桌面操作。

建议先实现 capability／presence／lease／receipt 的薄适配接口：

```text
ExecutorHost: id, kind, capabilities, platform, online,
              supportedActions, trustLevel, concurrency
```

第一版只接已有 local_mac；Windows 是本次 MCP 检查主机的环境，不等于 Kern 已有可交付的 Windows runtime。cloud_computer、browser_sandbox、remote_worker 保留为将来适配方向，不提前承诺。

执行路由优先级可借鉴 Bops 最新实现：**授权的 API／连接器 → 搜索与文本抓取 → 受控文件／命令 → DOM 自动化 → 视觉操作**。按任务、权限和能力选择，不强迫所有任务都去电脑上点鼠标。

## 五、优先处理的实测风险：连接器工具信任

### 5.1 当前检出与本地 origin/main 对应工作树仍有旧策略

`src/modules/connectors/policy.ts:28–34`：

1. `readOnlyHint=true` 优先判读；
2. 然后才检查 destructiveHint；
3. 无声明时凭 get／list／read 等名字推断只读。

本轮直接调用纯分类函数，得到：

```text
{name: "get_mutating_job"}                                 → read
{name: "read_and_delete", readOnlyHint: true,
 destructiveHint: true}                                  → read
```

这是**分类探针实测**，没有调用任何真正修改外部数据的工具，因此不等于已证明某外部服务遭到未授权写入。但它证明默认权限分类在这两个输入上偏宽。

### 5.2 候选工作树已经修复，优先交付而非重写

`.tmp-kern/integrate-main/src/modules/connectors/policy.ts:48–58`：

- 破坏性声明优先；
- 声明冲突按写；
- 无只读声明按写，名称不参与权限；
- 读变写强制停用，并给出 reconfirm 原因。

候选测试本轮 **10/10 通过**，包括 U01 边界。因此 P0 应是确认这组修复在最终候选中完整、对已保存工具快照执行刷新／重新分类、同一 head 验收后进入实际运行版本，而不是再创建另一份等价补丁。

**进一步安全建议**：MCP annotations 本身是服务器提供的提示，不是可验证的安全保证。即使声明只读，也应与受信服务器范围、工具 schema 指纹、人工安装审核、数据授权和运行时沙箱结合；不能让任意陌生服务器一句 readOnlyHint=true 就获得可信执行身份。schema／effect 变化应触发重新评估和必要的重新授权。

## 六、可执行改进路线与验收标准

以下工作量为单名熟悉本项目的工程师的粗估，不包含产品确认、跨分支冲突、数据库环境修复及外部供应商等待；不是已验证承诺。

|---|---|---|---|---|
| P0-A | 交付事实源收敛 | git worktrees、现有施工报告、版本指纹 | 一个指定候选 head；功能→提交→测试→运行实例清单；不重置／误收 WIP；确认 origin/main 是否需要刷新 | 0.5–1.5 天 |
| P0-B | 交付连接器信任加固 | 候选 policy、连接器快照刷新、现有 ToolBroker | 未声明／冲突／读变写不默认放行；旧快照刷新、撤权、参数变更、凭据重放均有测试 | 1–2 天 |

### 推荐第一轮只做这四项

1. **确认最终候选与已有修复归属**，尤其 U01 与批准卡，不急着新开功能分支。
2. **交付信任策略加固并复验旧工具快照**。
3. **统一任务卡＋“需要你”卡片的读取和导航**，默认折叠员工执行细节。
4. **跑三条真实闭环**：聊天专家任务、Mission 研究任务、本机待确认任务。

第一轮明确不做：Orgo 接入、动态创建 Bot、邮箱电话渠道、完整视觉 Computer Use、全角色无限自动派发。

### 三条端到端验收场景

**A. 产品研究**<br>
用户说目标 → 一个用户任务 → 专家真实执行与证据 → 缺数据只问必要问题 → 独立 QA → 结果回同一会话 → 业务 Gate 仍单独批准。

**B. 本机代码任务**<br>
显示本机在线／能力 → 展示明确 cwd 与授权范围 → 用户允许一次 → 执行、测试、变更回执 → 结果回原会话；拒绝、过期、动作变更均不得执行。

**C. 每周竞品观察**<br>
启用 Watch → 确认频率与来源 → Worker 重启不丢 slot → 无变化静默 → 变化落证据并去重 → 只把有行动价值的变化提交用户。
