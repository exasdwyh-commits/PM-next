# 外部 Agent 实测记录（Muse）对照分析

## 0. 这份材料的可信度

**是什么**：一位真实用户的使用自述，非官方规格、非第三方评测。作者自称「全文只收有
工具返回、文件落盘或用户确认的事实」，但带明显推荐倾向（含订阅价格、公开外链）。

**怎么用**：不把它当能力清单照抄。它的价值在于暴露**用户认为什么有价值**——
哪些环节让用户产生「这玩意真能干活」的判断。按这个口径读，它比任何竞品文档都准。

## 1. 一句话结论

**Kern 缺的不是 Agent 能力，是接口。**

内核成熟度上 Kern 不落下风，诚实纪律上明显更强。但截至今天，Kern **一个真实外部
系统都没有连上**。原文那 44 件事里，绝大多数的前提都是「已经连上了」。

## 3. 三个真差距

### 3.1 外部接入 = 0，被凭证保管缺位卡住

`resolveCollector()` 恒返回 null，意味着「信号雷达」目前是一个**结构完整但永远采不到
数据**的骨架。这个设计本身是诚实的（注释写明「采集时跳过绝不虚构」，比造假数据强得多），
但它把 Kern 锁在了「只能推理、不能取数」的状态。

阻塞点不在采集器，在凭证。schema 里「凭证有意不存这里」在没有连接器时是正确的减面决策，
现在它变成了硬阻塞。

**直接从原文偷两条设计教训**（作者踩过的坑，我们可以不踩）：

1. 他们的 Vault **每个 host 只能存一个凭证**，导致需要 `Client ID + API Key` 双 header 的
   系统接不进去，最后只能把其中一个降级存本地。→ Kern 的凭证层从第一版就要支持
   **一个目标多凭证 / 多 header 组合**。
2. 「用完即弃」的口令要真的能弃。→ 需要 ephemeral 凭证语义，不是只有长期存储。

这一条和我们本轮刚做完的清理是同一件事的两面：口令不该散在 `.env` 和脚本里，
该有一等公民的保管层。

### 3.2 身份层是死的

原文第一节：「Agent 上岗的第一课不是『回答问题』，而是『成为谁』。」后面用户对它的
情感联结（起名、三轮改头像、称其「有活人感」）显然是留存的主要来源之一。

Kern 已经有 `assistant-runtime/persona.ts`，也已经有 `SOUL.md` 这个文件和它的位置约定
（叠加在 CORE 之上、不得放宽硬约束）。**只是从来没接上。** 这是本文列出的所有事项里
成本最低、用户感知最直接的一条。

### 3.3 诚实没有被产品化

原文最有说服力的是第五节的三场排障：提出三个假设 → 做对照实验 → **自己的证据推翻了
自己的判断 → 当场收回**。作者的原话是「Agent 的价值不在从不出错，在用证据干活、
猜测标成猜测、错了就认」。

这恰恰是 Kern 整个架构的底色：`UNVERIFIED` 默认态、「未建档」而不是编分数、
「采集时跳过绝不虚构」、禁模型自评。**但这些在产品里都是静态状态，不是可见过程。**

Display Layer 刚落地，事件流基础设施是现成的。加三类事件即可把内部纪律变成用户看得见
的差异化：`node.hypothesis`（提出假设，标为猜测）、`node.refuted`（被证据推翻）、
`node.retracted`（收回结论）。这是我判断**投入产出比最高**的一条。

## 4. 建议（融进现有路线，不另起炉灶）

主干 P0-B..F 不改。三处调整：

| # | 建议 | 理由 |
|---|---|---|
| 1 | **P0-B 的第一个交付从「抓网页」改成「接通一个真实系统」**，并把凭证保管层作为 P0-B 前置 | 抓网页只解决「取证」；接系统同时解决「取证 + 干活」。Kern 定位是 Chief of Staff，要推进，不只是研究 |
| 2 | 身份层注入（SOUL → persona）与三类诚实事件，**并行插队** | 两项都是小改动，且都不依赖外部系统，不占 P0-B 的关键路径 |
| 3 | 不可逆动作清单落成 guard 测试 | Kern 已有 `WAITING_HUMAN` 与逐点确认，缺的是一份**可枚举、可测试**的清单。原文现成：花钱 / 发布 / 删除 / 对外发送 / 个人肖像 / 凭证 |

**先接哪个系统**（针对「做产品的人」）：文档与表格 > 日历与邮件 > 代码仓库。
理由：Kern 已有 cost-engine、产品/项目实体，产出天然是文档和表格；导出 MD/PDF 已经有了，
但那是**单向**的，接上文档系统才闭环成「改完回写」。

**一个零成本的好习惯**：原文作者上传文件后会下载回来核对 SHA-256、文档建完回读校验渲染。
Kern 已有 export API，加一步回读校验，几乎免费地把「产出可信」变成可验证的。

## 5. 明确不建议跟进的

- **云电脑代注册 / 代填验证码**：原文把「人在国内、用云电脑的 IP 去注册」当亮点。
  这有平台风控与合规风险，且偏离 Kern 定位。Kern 的 Desktop Runtime 一直明确
  **不等于** Computer Use，不要被这类演示带偏叙事。
- **视频产线 / 生图**：对营销环节有长期价值，但现在做会稀释主线。
- **堆连接器数量**（原文提到某一家 451 个工具）：Kern 的差异化是纵深——机会发现 → 验证
  → 研发 → 推进 → 营销 → 结果 → 复盘这条链。**接 3 个能闭环的，胜过接 11 个只能读的。**
