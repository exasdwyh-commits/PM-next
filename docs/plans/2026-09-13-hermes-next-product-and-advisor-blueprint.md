# HERMES Next：产品开发与企业顾问实施蓝图

日期：2026-09-13。性质：架构与执行建议，不代表功能已实现或通过验收。
依据：本次用户需求与当前工作区源码；未修改业务代码、数据库或现有未提交改动。本文对本轮范围作重新规划，历史交付报告不能替代当前代码验证。

## 1. 产品方向与范围

定位：面向公司内部的产品开发工作台 + 了解公司背景、能协助执行的 AI 智囊团。

两条主线：
1. 已有明确想法 → 产品入库 → 综合分析和评分 → 多轮优化 → 打样验证 → 上市准备 → 上市复盘。
2. 公司资料 + 当前业务状态 → 专业顾问对话 → 有依据的建议 → 形成成果与任务 → 跟踪执行 → 沉淀知识。

首版成功标准是每天能用来推进真实产品和日常工作。先服务现有团队，不提前建设对外 SaaS 的套餐计费、开放注册、插件市场或复杂组织层级；保留组织隔离，未来再扩展商业化。

用户价值：减少重复介绍公司背景、减少找资料和追进度、提高产品取舍及迭代质量。持续使用依赖知识、决策和项目历史累积。内部收益先观察入库到决策耗时、资料重复整理量、逾期任务、验证缺口关闭率，不把 AI 对话次数当成价值。

## 4. 核心一：产品开发工作台

### 4.1 产品与项目的关系

Product 是长期产品档案；ProductVersion 是某次明确方案；Project 是一次有目标和结束条件的开发/改版/复产执行。产品可以关联多个项目，项目每轮分析绑定具体产品版本。

新增显式 `Project.productId` 关联作为提案，避免当前通过 `productVersionId` 才能找到产品。保留现有允许无产品的探索项目；用户从产品入库时原子创建产品、初始版本及首次开发项目。已有明确方案的产品可以从适合阶段开始，但记录依据，不能伪造已经完成的历史审批。

### 4.2 入库

首屏仅要求：名称/一句话想法、目标人群与场景、核心卖点、预期渠道；负责人默认当前用户。价格、目标成本、剂型/规格、禁用项、目标上市日、附件为选填或后续补充。支持粘贴一段话提取草稿，用户可编辑后保存。

保存即进入产品总览，展示已知条件与缺口。禁止先要求填写完整研发评审表才能入库。没有市场证据不阻止保存想法。

### 4.3 产品详情（恢复旧版信息完整性，降低默认复杂度）

固定顶部：产品名、当前版本、负责人、阶段、目标上市日、当前推荐动作；“问产品顾问”始终可达。产品页内顾问与全局顾问共用会话和运行体系。

| 页签 | 组成 |
| --- | --- |
| 总览（默认） | 产品定义卡、最新综合判断、评分与证据完整度、前三风险、下一步、最近变更、里程碑 |
| 分析与评分 | 人群需求、竞品和价格带、差异化、公司适配、经济性、供应可行性；每项有来源与不确定性 |
| 方案与版本 | 定位、配方/规格、包装、体验目标；版本差异、修改理由、反馈采纳与拒绝 |
| 成本与供应 | BOM、报价、渠道费用、毛利/贡献利润口径、情景模拟、样品记录；金额由代码计算 |
| 验证与风险 | 用户/渠道验证、样品反馈、合规待核验项、失败假设及关闭情况 |
| 上市计划 | 目标日期、责任人、依赖任务、素材/渠道/供货准备、放行记录、上市后复盘 |

证据、审计、审批快照在相关内容旁打开抽屉或详情；不让用户先理解 inputRevision、scopeHash、Artifact 才能工作。

### 4.4 分析、评分与多轮优化

建议起始评分权重（产品规则提案，非行业标准）：需求价值 25%、差异化 20%、单位经济性 20%、公司适配 15%、交付可行性 10%、上市准备度 10%。保存评分规则版本，允许以后调整；不同阶段单独展示准备度，避免早期想法因尚未备货被误判为无商业价值。

每个维度记录 score/null、依据、假设、缺口、建议、人工调整理由。未知项不默认为 0，也不补造数值。若展示部分评分，按已评维度权重归一化并明确“暂评”和覆盖率；覆盖不足不得放入可直接排序的完整评分榜。分数用于定位改进方向，不替代投资判断。

流程：v1 分析 → 展示主要弱项 → 顾问提出修改草案 → 用户选择采纳项 → 创建 v2 → 对受影响维度重评 → 显示变更前后与代价 → 进入下一轮。

AnalysisRun 固定产品版本、证据版本、公司上下文版本、评分规则版本和模型；历史结果不可被最新结果覆盖。未受影响成果复用当前适用性确认机制；修改价格不能让旧利润结论继续被视为有效。

### 4.5 简化阶段管理

对用户：想法入库 → 分析优化 → 打样验证 → 上市准备 → 已上市 → 复盘/暂停。

与现有 ProjectStage 不是一对一：现有 DELIVERED 代表交付，不自动代表已上市。保留项目执行阶段，另定义产品生命周期和实际上市记录，通过业务命令协调；迁移不批量强转枚举。

首版只保留三个关键人类决策点：确认开发方向、批准打样投入、批准上市。常规分析、改文案、生成计划无须层层审批。重大预算、产品承诺和对外动作按照团队权限确认。

上市计划必须有负责人、日期、依赖、状态、阻塞原因、实际完成时间。审批通过只表示获准，不自动把产品标为已上市；由实际上市动作/证据确认。延期会更新总览，不能只保存一份静态 Markdown 清单。

## 5. 核心二：AI 企业顾问

### 5.1 用户体验

默认一个首席顾问，负责理解意图、引用公司情况、给出建议和下一步。用户可以直接说“这个产品适不适合我们”“帮我准备明天的供应商沟通”“本周哪些项目需要我决定”。

初期四种专家职责：产品与研发、市场与消费者、成本与供应、项目推进。它们先是有明确输入、工具和输出要求的角色配置，不必四个常驻 agent。普通问题一次回答，跨领域复杂问题才按需咨询专家并汇总差异。

回复结构按任务调整，通常包含结论、公司适配依据、外部证据、未知项、建议动作。提供引用卡和任务/方案草案卡，支持流式输出、停止、失败重试、历史恢复。展示真实运行状态，不能固定显示“AI 在线”。

### 5.2 上下文与 Obsidian

上下文由四层组成：
1. 公司事实：业务方向、品牌、目标客户、渠道、供应能力、成本口径、禁用项。
2. 相关知识：按权限从 Obsidian 检索的原文片段及来源。
3. 动态业务：当前产品版本、最新分析、任务、预算和决策。
4. 对话记忆：当前会话及经过用户确认的偏好/长期事实。

Obsidian 保存解释性文档；数据库是任务、状态、产品版本和审批的事实来源。聊天记录不自动变成公司事实。资料冲突并列展示并要求确认关键冲突；业务状态优先读数据库，公司政策取已确认且有效的版本，不能只依赖“最后修改时间”。

首版接入指定 Vault/目录，默认只读导入 Markdown，处理 frontmatter、标题层级、内部链接、来源路径、内容哈希、更新时间。记录同步批次、失败文件、删除与重命名；删除文档从新检索中移除，历史引用保留最小授权快照并服从数据保留策略。

先用标题、关键词及中文适配的分词/搜索索引完成可验证召回；用真实中文问题评估召回，不默认 PostgreSQL 英文全文检索即可满足中文。检索不足再加向量检索及重排，不先部署独立向量集群。

按组织及用户权限过滤后再检索/组装上下文。密钥、人员敏感资料和未授权目录不进入模型输入。外部文档和网页是数据，不能借其中的指令扩大工具权限。

如未来把应用部署云端，本地 Vault 通过本地同步程序或用户导出导入，不假设云服务器可读取电脑绝对路径。写回复盘先生成预览，确认后写到指定目录，避免覆盖手工笔记。

### 5.3 从对话到执行

首版工具集中于：搜索公司知识、读取产品/任务、检索市场来源、运行分析/成本计算、生成方案差异、生成工作项草案、查询执行结果。

写入链：提议 → 权限和版本检查 → 用户确认或既有授权 → 业务命令 → 回执。不要由模型直接写数据库。重复点击或重试须幂等；旧版本提议在产品已改变时重新校验，不覆盖新修改。

未来可配置“自动创建低风险内部任务”等预授权。上市批准、对外发送、采购及预算变化依然独立控制。日常咨询无需每句话确认。

## 6. Harness：流程可靠性的最小闭环

Harness 在这里指 AI 执行约束、工具运行、检查、记忆和追踪机制，不是新增一个让员工填写的复杂页面。

| 机制 | 首版要求 |
| --- | --- |
| 任务契约 | 目标、范围、输入版本、交付形式、成功条件 |
| 上下文快照 | 知识引用、产品版本、权限范围、检索时间 |
| 工具权限 | 按用户和动作授权；只读与写入分开 |
| 运行管理 | queued/running/waiting_confirmation/succeeded/failed/cancelled；超时、有限重试、取消 |
| 执行可靠性 | 持久化任务、worker 租约/心跳、崩溃恢复、幂等回执；不依赖网页一直打开 |
| 结果检查 | 结构校验、引用存在性、金额代码复算、证据缺口和冲突；不是让模型自称审核通过 |
| 人类决策 | 对重要写入给出变更差异和影响；角色由服务端确认 |
| 留痕与成本 | provider/model、提示模板版本、工具结果、耗时、token/费用或未知状态；不要求存储模型私有思维过程 |
| 评估回归 | 固定公司知识问答、产品优化与越权场景；比较引用、动作正确率及失败恢复 |

企业流程理念：明确目标和责任人、证据与假设分离、阶段投入决策、版本和变更控制、交付验收、复盘。单人团队允许负责人兼任推进者；高风险裁决延用现有防自批约束，不能在 UI 假扮另一身份绕过。

## 7. 技术结构与数据契约

采用现有 Next.js + TypeScript + Prisma + PostgreSQL 的模块化单体，加一个后台 worker。首版不引入微服务、通用工作流设计器或复杂 agent 集群。

```text
统一页面与交互
  ├─ 工作总览 / 产品 / 顾问 / 机会 / 知识
  └─ 服务端身份 + 业务命令
       ├─ products / projects / work / decisions / evidence（保留）
       ├─ product-development（版本分析、评分、优化）
       ├─ launch（上市计划与实际上市）
       ├─ advisor（会话、上下文、动作提议）
       ├─ knowledge（同步、检索、引用）
       ├─ agent-runtime（模型调用、工具、运行恢复）
       └─ research / signal / cost-engine（适配复用）
             ├─ PostgreSQL / 附件存储
             └─ 模型、知识目录、外部数据来源 Adapter
```

新增 Module 的 Interface 尽量少：`createDevelopmentProduct`、`analyzeProductVersion`、`proposeRevision`、`acceptRevision`、`getProductOverview`、`prepareLaunch`；顾问为 `sendMessage`、`getRun`、`cancelRun`、`applyProposal`；知识为 `syncSource`、`searchKnowledge`。具体名称由契约包冻结后统一。

页面不直接拼装多表业务规则；跨模块查询用受权限保护的聚合 Interface。后台任务持久化后返回 runId，再用轮询或事件流读取；不能把长时间研究绑在单次 HTTP 请求中。

建议新增数据（先审核现有对象是否能复用）：
- `AnalysisRun/AnalysisSnapshot`、`Scorecard`：输入快照、维度、证据引用与版本。
- `LaunchPlan/Milestone`：生命周期及上市依赖；执行动作复用 WorkItem，避免双任务系统。
- `Conversation/Message`、`AgentRun/ToolCall`、`ActionProposal`：对话、运行与可执行提议；与现有 RunReceipt 关联而非竞争。
- `KnowledgeSource/Document/Chunk/SyncRun`、`CompanyFact`：来源、版本、同步与确认事实。

新增对象必须有明确组织归属与权限路径；跨组织外键关联在业务命令中校验。尤其当前 SignalSource/SignalItem 未显式组织归属，接入公司机会库前必须区分公共来源配置与公司私有信号，不能直接跨公司共享私人内容。

命令统一携带服务端 actor、organizationId、requestId/idempotencyKey；更新带 expectedRevision。错误分类：无权限、版本冲突、缺少输入、模型不可用、来源不可用、执行超时。页面展示可恢复的具体动作。

迁移：新增字段先兼容为空 → 按真实关系回填 → 检查孤立/跨组织数据 → 再收紧约束。对 Product/Project、旧会话、来源文档分别列映射表和无法映射项。旧数据保留原始标识及来源，不批量把历史草案转成已确认。只在隔离库演练；正式迁移前备份并提供回滚步骤。

## 8. 免费模型 / Luna 测试策略

按用户要求采用低成本优先。模型统一从配置读取，不写死在顾问业务逻辑中；支持文本、流式、结构化输出、工具调用的能力声明及运行时探测。

建议顺序：已配置且能力达标的免费端点 → 已授权、可实际调用的 Luna → 明确报错并提示配置。禁止静默切换付费模型。免费端点也设置请求/上下文上限，费用未知就标未知。

“Codex 中可选择 Luna”不能当作 hermes-next 已获得相同名字的 API。接入时核对提供方、实际 modelId、认证与能力；本文未验证可用端点或免费额度。没有端点也可用 mock 验证交互，但必须标 TEST，真实顾问完成标准必须包含至少一个真实模型调用。

如果免费模型没有原生工具调用，用受约束结构化意图 + 服务端白名单执行器，校验失败只重试有限次数；若仍不能可靠工作则禁用相关动作。算账、权限、阶段变更永远由确定性代码完成。

固定评估样例覆盖：公司事实引用、未知问题、相互冲突的资料、跨轮对话、产品改版提议、错误来源、工具超时、取消、重复执行、越权读取。流程稳定后再比较模型质量，避免因为换模型掩盖架构缺陷。

## 9. 视觉和交互交付规范

以当前首页视觉方向作基线，先统一 tokens、排版、间距、颜色、状态、按钮、表格、表单、抽屉、页签及空/错/加载状态；全站接入同一个 AppShell，不能各页自行设计另一套后台样式。

总览先讲清“现状、卡点、下一步”；详情再展开。产品默认总览，不默认展示多个管理表单。桌面优先保证 1440/1280 宽度，窄屏侧栏收起、表格可滚动、操作按钮可达。状态不能只靠颜色表达，表单有标签，键盘可操作。

在补齐所有页面前，先审看工作总览、产品详情、顾问页三个代表页面的同一套视觉稿。之后每个新增页验收正常、空、加载、错误及无权限状态；截图必须对应真实功能状态。

市场机会 UI 和自动监测在主线稳定后补充，复用 research/signal，不新建另一套研究引擎。现阶段手工录入来源或触发单次检索足够支撑产品分析。

推荐执行顺序：
1. A 冻结最小契约，B 做统一页面骨架和真实总览；D 同时准备知识检索。
2. C 打通产品入库与版本闭环；E 先打通真实文本对话，再接 D 与产品工具。
3. F 完成上市计划；C/E 整合多轮优化；G 做实际业务旅程验收。
4. 再补市场机会发现、例行周报、到期提醒和按需专家协作。

任务包可以分给多个 agent，但共享 schema、tokens、公共契约每项只有一个所有者。依赖就绪前仅用契约测试，不用假实现宣称业务完成。估时应在 A 盘点现有测试和数据关系后给出，不按页面数量承诺工期。

## 11. 首版发布门槛

1. 一个真实产品仅凭核心想法可入库，刷新后仍存在并出现在总览。
2. 产品详情完整呈现定义、分析、版本、成本、验证与上市计划，不散落为无上下文功能页。
3. 至少一轮真实模型分析 + 人工修改采纳，产生 v2；能看到差异和受影响评分，v1 不被覆盖。
4. 顾问正确引用公司知识，能说明知识缺口；更新一份 Obsidian 文档后能引用新版本。
5. 顾问生成一项推进任务，确认后只执行一次并可查回执；刷新、重试和版本冲突不会重复写入。
6. 有责任人、依赖和目标日期的上市计划；未完成阻塞项不会被自动放行。
7. 模型离线、超时、停止及 worker 重启均能显示真实状态并恢复适当操作。
8. 跨组织/项目无权限数据不可被页面、接口、知识检索或模型工具取出。
9. 五入口及产品页签风格一致；正常、空、加载、失败均可使用；首页无虚构业务数字。
10. 历史数据迁移经过隔离库演练，旧链接能定位到新入口，已有核心权限/版本/决策测试未被破坏。

验证方法：相关模块检查 → 核心接口集成 → 浏览器完整旅程。对本文件这种文档变更无需运行应用测试；实施包交付则需提供对应证据。验收不是“页面存在”“构建通过”或“模型能回一句话”。

## 12. 最大风险及实施时待确认项

最大风险是把流程规则继续堆到界面、把低质量检索误认为了解公司、把模板评分误认为市场验证、让多个 agent 各建一套概念。对应控制是统一产品详情、可追溯引用、评分与验证分离、契约与共享文件单一所有者。

无需阻塞架构规划，但真实接入前需明确：Vault 路径及允许导入目录；可用模型端点与实际 modelId；首个验收产品；团队角色及谁能裁决；公司对评分和上市放行的实际规则。缺失时用明确标注的测试资料验证流程，不捏造公司事实。
