# Kern 成熟强化：阶段 A

## 目标与顺序

先强化现有功能的执行、安全、恢复和交付，再统一前端体验、逐项引入成熟能力，最后评估视觉操作与多执行主机。

本批仅处理连接器工具信任及升级兼容，不改变业务 Gate、本机授权规则、模型路由或数据库结构。不合并其它报告、主题、批准卡分支，也不直接更新 main 或运行中的服务。

## 连接器安全契约

1. 只有显式只读且没有破坏性冲突的工具，才能按读分类；名称不决定权限。
2. 无声明、声明冲突及明确写工具，默认停用；显式重新允许后仍走受保护能力和单次审批。
3. 升级时不依赖用户先刷新：持久化工具缺少分类依据、或只读权限字段不一致时，读取即降为写并停用，附中文原因。
4. 已显式启用的写工具可保留开关，但 capability 由当前策略重建，不接受旧的读取权限旁路。
5. 设置页与执行器使用相同的安全投影；投影不得修改原记录，重复执行必须幂等。
6. 用户关闭的工具保持关闭；刷新声明不能静默重新启用。
7. 重新允许不是批准本次外部写入，实际调用仍需匹配动作的审批凭据。
8. MCP annotations 是服务端声明，不是独立安全证明；该规则不取代服务器安装审核、数据授权与出站限制。

## 实现位置

- `connectors/policy.ts`：发现时分类、分类依据和原因、安全读取历史快照。
- `connectors/index.ts`：列表、刷新、设置和执行器加载统一读取快照。
- `connectors/runtime.ts`：对直接传入的快照再次做安全投影，再注册 ToolBroker 工具。
- `muse/components/sheets.tsx`：显示分类依据与需要重新确认的原因。
- `tests/kern-connectors.test.ts`：覆盖新旧快照、失效字段、权限重绑定及模拟 MCP 写调用拦截。

```bash
node --import tsx --test tests/kern-connectors.test.ts tests/desktop-confirm.test.ts tests/kern-protected-actions.test.ts tests/architecture-layers.test.ts tests/kern-runtime-architecture.test.ts
npm run test:regression-units
```

连接器用例使用本地模拟 MCP 服务，不执行真实外部发送或删除。现有 Quality CI 的 `test:regression-units` 已包含该测试文件，不需要新增工作流权限。

验收需包含先红后绿的运行时回归：旧只读快照不得暴露工具；写工具即使保存了读取 capability，也不得把调用送到模拟外部服务。

## 升级与运行边界

- 不运行数据库迁移，不批量改写用户快照，不修改原有工作树中的未提交改动。
- 部署新版本后，新加载的工具立即适用安全投影。历史读工具可能先停用，这是有意的保守变化。
- 用户可先刷新声明，再明确启用；无法证明只读的工具只能作为写工具启用并逐次确认。
- 部署时要协调 web 与 Worker 的版本和重启；已经在旧进程中加载的工具闭包不受本批代码追溯修改。
- 回退应用版本不会自动恢复被用户设置操作持久化的旧开关；不得为恢复便利重新引入名称判读规则。
- 本批不声称验证了真实外部 MCP 的副作用、完整数据库端到端、浏览器交互或生产环境部署。

## 后续队列

本批安全修复通过 review 与 CI 后，继续：

1. 现有 Worker、任务取消、租约与原会话回执的真实闭环核验。
2. 已有批准卡／报告成果的独立集成与同版本验收，不把不同工作树结果拼成一个通过结论。
3. 定时任务认领后崩溃的持久化恢复、slot 幂等与失败可见性。
4. 在现有执行模型上整合用户任务卡与“需要你”，不新增平行执行状态机。
5. 有界专家咨询、结构化 Watch 等低风险增量。

每批独立提交与 PR，明确已有能力、已验证能力、环境阻塞和未实施范围。
