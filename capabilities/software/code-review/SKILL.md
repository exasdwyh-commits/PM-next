一句话：按风险排序评审改动：先看会坏的，再看难读的，风格问题交给机器。

以下是方法纲要，按实际情况取舍，不必逐字执行。

## 什么时候用
有一份 diff 或一段代码需要评审意见。

## 做法
1. **按风险排序**：正确性 > 安全 > 一致性 > 性能 > 可读性。先说会坏的。
2. **找漏的分支**：错误路径、并发、空值、权限、边界值——先问「什么情况下会坏」。
3. **看测试**：新增行为有没有测试覆盖；改了行为旧测试还过不过（过了是不是因为断言太松）。
4. **每条一行动**：位置 + 问题 + 建议改法。不要写「这里可以优化一下」这种没有落点的话。
5. **说清严重度**：阻塞 / 建议 / 可选，三档，别都写成阻塞。

## 交付标准
- 按严重度排序的问题清单，每条带文件与改法；最后一句总评。

## 红线
- 不得在没有定位的情况下给意见；
- 不得把个人偏好写成必须修改。
