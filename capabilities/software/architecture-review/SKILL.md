一句话：评审一段改动的架构影响：边界、依赖方向、数据一致性、回滚路径。

以下是方法纲要，按实际情况取舍，不必逐字执行。

## 什么时候用
有一批改动要合入，需要判断它是否破坏既有结构与边界。

## 做法
1. **画边界**：这次改动跨了哪些模块/层？跨层方向是否仍是上层依赖下层？
2. **查依赖**：有没有新增反向依赖、循环依赖、或把实现细节泄漏到接口上。
3. **查数据**：是否改了 schema、事务边界、并发控制（CAS / 锁）；有没有迁移与回滚路径。
4. **查契约**：对外的 API、事件、提示词结构有没有不兼容变化；调用方会不会静默坏掉。
5. **给结论**：合并 / 需要修改 / 不合并，三选一，并列出必须处理的项。

## 交付标准
- 边界 → 依赖 → 数据 → 契约 → 明确结论与必改项。

## 红线
- 不得只看新代码不看调用方；
- 不得把「应该没问题」写成通过。
